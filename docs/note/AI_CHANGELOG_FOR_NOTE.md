# BigBonusBlitz 制作記録の整理版

## この記事の目的

この資料は、BigBonusBlitzをAIと一緒に作るとき、見た目の改善だけでなく「なぜその変更をしたか」「どう失敗を見つけたか」「何を証拠に完了としたか」を再現できるようにまとめたものです。完成品の宣伝文ではなく、制作中の判断と失敗を含む作業記録です。

数値は実測条件があるものだけを書き、添付画像に写っている数値はゲームの仕様として扱いません。実機・配布ビルド・プレイヤー評価をしていない項目は未検証として残します。

### 2026-09-22：制作記録を引き継げる形へ整理

会話だけでは、別のAIが「依頼」「採用した設計」「実装済み」「検証済み」「まだ試していない」を区別できません。そこで、全履歴の正本を `docs/AI_HANDOFF_HISTORY.md` に置き、判断の短いログを `docs/devlog.md`、本人の原文を `docs/note/MEMO.md`、記事へ入れる前の材料を `docs/note/MATERIAL.md` に分けました。会話に正確な日時がない依頼は、日付を推測せず会話上の順序として記録しています。

今回の整理自体も制作履歴の一部です。Unityのお知らせには `dev 312` として登録し、次のAIはこの資料を読んでから対象画面のC#、JSON、QA画像を確認します。

## 1. 日付順の制作記録

### 2026-05-29〜09-06：基礎を作り、ブラウザ版の知識を整理

Git上の初回記録は2026-05-29です。スロットの抽選、リール、ボーナス、敵、タイトル、音、画面を少しずつ足しました。初期の反省は、会話だけで決めると決定が消えることでした。仕様、現在地、失敗、未検証をファイルへ分ける方針は、この後の作業すべてに影響しました。

### 2026-09-07：Unityへ移行

Unity 6.3、Universal 2D、uGUIを使い、ゲームの制御部分はUnity非依存のC#にしました。抽選や条件を直接テストできるようにしたため、見た目の修正をしてもゲームの確率を同じ検査へ通せます。

### 2026-09-08：1,104,000通りを調べる

23フラグ、6通りの押し順、20³の押し位置を全数検査しました。最初の制御ではハズレなのに役が揃うケースが340件ありました。スコアが高い停止位置を選ぶ方法をやめ、残りのリールで詰まない候補を先に残す方式に変えました。メモ化で10分以上かかる検査が約6秒になりました。

### 2026-09-09〜10：冒険、AT、資源、ショップの意味を決める

ATを洞窟のゾーン型にし、ライフ、ソウル、エンバーを別の目的に分けました。ソウルは成長、エンバーは回転や補給、ライフは探索の余力です。確率はコードに書かず、JSONの表で持つ方針にしました。装備の強化、補給、ステータスの入口としてショップを作りました。

この時期の失敗は、機能を入れたことだけで完成と判断したことです。松明を入れたのに25万Gで一度も尽きなかった、ATと通常のエンゲージが同時成立した、JSONの既定リストが追記されて敵が3体から6体になった、という問題は、通しテストを追加するきっかけになりました。

### 会話上の順序（正確な日付は記録なし）：タイトルキャラの揺れを細かくする

本人から、タイトルキャラの剣が揺れで歪む、白いリボンが髪と一緒に揺れる、前髪と横の垂れ髪を分けたい、髪の中央だけが大きく揺れて毛先が揺れない、あほげも揺らしたい、スカートをめくれるようにしたい、肩を支点に剣を上げ下げしたい、太ももが揺れるのはおかしい、目が揺れる、髪が揺れすぎる、という順で指摘がありました。

正式なLive2D Cubismではなく、Unityのレイヤー画像と共通シェーダーを使う擬似Live2D方式にしました。髪・リボン・あほげ・スカート・剣を別の強さで動かし、顔と目を保護範囲で固定しました。毛先側の変形場を強め、剣は肩支点の揺れに分離しました。10時刻の剣姿勢、目パチ、手の不変条件、前髪差分を隔離Unityで確認しています。

ここから得た教訓は、揺れの強さを全身に掛けると、動いてほしくない目・手・太ももまで動くことです。パーツの名前を分けるだけでは不十分で、変形場と保護範囲を同じ座標系で設計する必要があります。

### 2026-09-11〜13：モーションに音を付ける

「各モーション全てにSound効果音をつけたい」という依頼から、hover、click、open、close、purchase、recover、denied、cloth、swordなど21キューを整理しました。Updateのたび、頂点ごと、目パチごとに鳴らすと音が連打になるため、意味のある開始・接触・完了の1回へ限定しました。8ボイス、クールダウン、ミュート、既存戦闘音優先を実装し、波形の無音・有限値・両端の余裕を隔離検証しました。

### 2026-09-14〜20：背景を「絵」から「組み替えられる層」へ

冒険中の背景は、遠景・中景・近景を別々にして奥行きを作り、時間帯と天候をUnityのエフェクトで変更できるようにしました。30地点、90層、朝・昼・夕方・夜、8天候を実装しています。

シームレス化では、画像を単純に16%透かして混ぜると木・塔・柱が二重に見えました。左右22%の候補から色差が小さい接続経路を求め、実際に混ぜる範囲を2.4%へ狭め、座標だけを1pxテクスチャへ保存しました。原PNGは変更しません。2026-09-20の検証では30地点・90層の周期境界を調べ、worstPeriodDifferenceは2.19708832607117E-06でした。

## 2. 見た目を改善するときの手順

1. 参考画像から「色」「視線の順番」「面の分割」「操作状態」を抜き出す。画像内の文章や数字をそのまま仕様にしない。
2. 既存のゲーム状態、コールバック、購入、保存、音を先に読む。見た目だけ作ると、実際の価格や上限が外れる。
3. 背景、枠、アイコン、文字を別素材にする。文字や価格を画像に焼き込まない。
4. 最初から通常、選択中、購入可能、通貨不足、最大、所持上限、長い名前を設計する。
5. 画面幅を決め、安全領域と下端余白から位置を計算する。アイコンの幅も文字領域から引く。
6. Unityの実画面を1280×720と2556×1179で描き出す。HTMLは比較用であり、完了の証拠ではない。
7. 目視だけでなく、兄弟テキストの重なり、文字のクリップ、操作領域、状態遷移、購入の再判定を自動検査する。
8. 変更のたびに、採用理由・不採用案・検証条件・未検証の範囲を日付付きで残す。

## 3. AIが再現するときの設計契約

### 画面

- 常時表示の情報面は不透明にする。動く背景を透かさない。
- 主ボタンは画面に1つ。通常ボタン、戻る、無効を色と文言で区別する。
- 行やカードの状態は、色だけでなく、選択線・価格・文言でも示す。
- 文字はUnity Textなどの生UIにし、6桁の数値と長い日本語を最初から検査する。

### キャラクター

- 共通の揺れを全身に掛けず、髪束、リボン、あほげ、衣装、剣を独立パラメータにする。
- 目、顔、手、太ももなど動かさない場所は保護領域にする。
- 毛先を大きくする場合も、根元との連続性を同じ変形場で保つ。
- 剣やリボンは「髪と同じ」ではなく支点と固有の遅れを定義する。

### 背景

- 遠景・中景・近景・天候・時間・局所光を分離する。
- ループは左右反転でごまかさず、実アルファと色差を測って接続座標を作る。
- 代表地点で12条件を確認してから全地点へ広げる。

### 検証

- 変更したコードだけでなく、実際の生成経路（GameController/MapScreen）を通す。
- SaveDataは隔離コピーで無効化し、ユーザーのセーブを使わない。
- PNGとvalidation.jsonは消さず、v1、v2のように増やす。
- 「Unityで表示した」「実機で触った」「プレイヤー評価を得た」を別の事実として書く。

## 5. 事実として書かないこと

- 添付画像の数値をゲームの既定値とすること。
- 擬似Live2Dを正式Live2D Cubismと呼ぶこと。
- 実機、配布ビルド、聴感、プレイヤー評価を実施済みと書くこと。
- 生成画像が一度で完成したと書くこと。透過不良の金枠を不採用にした記録も残す。
- 画像生成プロンプトだけで、同じ操作や状態が再現できると書くこと。実装とQAが必要。

# docs/note — 販売用note（制作過程）の入口

**新しいセッションはこの1枚を読めば続きから書ける。** `/clear` の後もここから入る。

---

## 0. これは何か

BigBonusBlitz を AI に作らせた過程を、有料note として売るための原稿一式。

- 売り方: 単発の有料note。980〜1,500円（本人決定・2026-09-10）
- 構造: B（AIに作らせ続ける仕組み）+ C（壊れた箇所の全開示）の混合（本人決定・2026-09-10）
- 読者: 非エンジニア。コードを書かない人（本人決定・2026-09-10）
- **公開のタイミング: ゲームの完成と同時**（本人決定・2026-09-10）。それまでは書き足し続ける

## 1. ファイルの役割

| ファイル | 役割 | 誰が触るか |
|---|---|---|
| `README.md` | この入口。方針と次の1手 | 方針が変わったときだけ |
| `note-01-ai-game-making.md` | 記事の本体。これを note に貼る | 節目でまとめて更新 |
| `MATERIAL.md` | 材料の置き場。失敗・数字・決定を時系列で貯める | **毎セッション追記する** |
| `images/` | note に貼る画像10枚と、足りない分のショットリスト | 画像を足すとき |
| `build_images.py` | 画像の生成スクリプト。`py -3 docs/note/build_images.py` | 図解を直すとき |
| `insert_images.py` | 記事への差し込み。実行済み（再実行しても二重に入らない） | 基本さわらない |

**原則: 気づいたことは `MATERIAL.md` に足す。記事本体は節目にまとめて直す。**

記事本体を毎回いじると、文体と構成が崩れる。材料だけ先に貯める。

## 2. 毎セッションやること（BBB の作業をしたら必ず）

BBB のコードや仕様を触ったセッションは、終わりに次を1回やる。

1. `MATERIAL.md` の「未整理の材料」に追記する。書式は同ファイルの先頭にある
2. 追記したのが**失敗**なら、外部知能の `errors/ERRORS.md` にも記録する（重複ではない。あちらは再発防止、こちらは記事の材料）
3. 数字が出たら、出どころ（どのテストの実測か）を必ず併記する

追記は3行で足りる。整形はしない。整形は記事にする時にまとめてやる。

## 3. 記事本体を更新するタイミング

次のどれかが起きたときだけ、`note-01-ai-game-making.md` に反映する。

- `MATERIAL.md` の未整理が10件を超えた
- 章の完成・リリースなど、ゲーム側で節目があった
- 本人から「記事を更新して」と言われた

更新の手順:

1. `MATERIAL.md` の未整理を読み、記事のどの節に入るか割り当てる
2. 該当節だけ書き足す。他の節は触らない
3. 「壊れた箇所カタログ」に足したら、**件数を全部の箇所で直す**（タイトル・目次・型の分類・締め）
4. `skills/story-sales-copy/references/review.md` の4パスを回す
5. `MATERIAL.md` の該当行を「反映済み」へ移す

## 6. 書くときの決めごと

- 一人称は「私」。文は短く切る。箇条書きを多用する
- 数字は捏造しない。出どころを言えない数字は書かない
- 「必ず作れる」「誰でもできる」と書かない。事例1件と再現性を混同しない
- 引用と実測を混ぜない（記事中の失敗⑩がまさにこれ）
- 太字は節あたり2〜3箇所まで。強調は `"…"` を使う
- 技術用語は必ず言い換える。読者はコードを書かない
